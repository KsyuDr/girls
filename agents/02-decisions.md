# Журнал решений

Формат: **решение** — почему. Новые решения добавляйте в конец с датой.

## 2026-11-10 — старт бэкенда

1. **MVP прежде всего, инкрементная модель (ЛР3).** Каждый этап доводим до рабочего состояния
   с тестами, потом следующий. В крайности не уходим.
2. **Бэкенд: Python 3.13 + FastAPI**, SQLAlchemy 2 (async) + asyncpg, Alembic, Pydantic v2,
   зависимости через `uv`. В ЛР1 был Node.js — заменили, итоговый выбор оставляли за командой.
3. **БД: PostgreSQL 17 в Docker** (`docker-compose.yml` в корне). Порт на хосте **5433**,
   чтобы не конфликтовать с локально установленным PostgreSQL на 5432.
   Для тестов отдельная база `safe_city_test`.
4. **Монорепозиторий**: `backend/` и `frontend/` в одном репозитории, в отдельных папках.
5. **Вход: телефон + одноразовый код → JWT** (Bearer). Паролей нет. В dev/test код
   фиксированный (`SMS_MOCK_CODE`, по умолчанию `0000`); реальный SMS-провайдер подключается
   позже без изменения API.
6. **«Панель служб» = панель модератора.** Роль `moderator`; экран тот же, смысл другой
   (никаких реальных служб).
7. **«Помогу» и «Потеряно/найдено» закладываем в модель данных и API сразу**,
   интерфейс во фронте — следующими этапами.
8. **API повторяет контракт `frontend/src/services/api.js`** (те же URL под `/api`, JSON в camelCase).
   Минимальные правки фронта делает бэкенд-разработчик: токен в заголовке, шаг ввода кода,
   `VITE_USE_MOCK=false`, адаптеры в `api.js`.
9. **Бэкенд — чистый REST**: мутации возвращают созданный/изменённый объект. Если компонентам
   фронта нужен весь список (как сейчас в моках), `api.js` сам перезапрашивает список.
   Компоненты страниц при этом не меняются.
10. **Оформление — забота фронта.** Цвета, иконки, «12 мин назад», «650 м» сервер не хранит.
    Сервер отдаёт `level`/`type`/`category`, ISO-время `createdAt`, координаты и расстояние
    в метрах (если передать свои координаты). Исключение — статичные справочники
    (службы, памятки): там иконка/цвет — часть контента.
11. **Справочники (службы, памятки, типы меток, категории карты, города) — статичные данные
    в коде бэкенда** (`app/reference/`), отдаются через `GET /api/reference`.
    Пользовательские данные и справочные точки карты (`places`) — в БД.
12. **Чтение публичное, запись — только с токеном.** Карта, лента и справочники доступны без
    входа; создание меток, SOS, контакты, отклики — после входа; панель — только `moderator`.
13. **Фото** храним на диске в `backend/media/` и раздаём как статику `/media/...`;
    до 4 фото на метку, jpg/png/webp, до 5 МБ.
14. **Push/WebSocket в MVP нет** — фронт перезапрашивает данные. Реалтайм — после MVP.
15. **Стиль кода обязателен**: ruff (бэк), ESLint + Prettier (фронт), pre-commit-хуки,
    сообщения коммитов в формате Conventional Commits. CI на GitHub Actions повторяет проверки.
16. **После каждого этапа — автотесты (pytest) + ручная проверка в браузере**
    (встроенный браузер Claude или Helium MCP): Swagger `/docs`, а после интеграции — сам фронт.
