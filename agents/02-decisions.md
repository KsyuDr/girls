# Журнал решений

Формат: **решение** — почему. Новые решения добавляйте в конец с датой.

## 2026-11-10 — старт бэкенда

1. **MVP прежде всего, инкрементная модель (ЛР3).** Каждый этап доводим до рабочего состояния
   с тестами, потом следующий. В крайности не уходим.
2. **Бэкенд: Python 3.13 + FastAPI**, SQLAlchemy 2 (async) + asyncpg, Alembic, Pydantic v2,
   зависимости через `uv`. В ЛР1 был Node.js — заменили, итоговый выбор оставляли за командой.
3. **БД: PostgreSQL 17 в Docker** (`docker-compose.yml` в корне). Порт на хосте **5433**,
   чтобы не конфликтовать с локально установленным PostgreSQL на 5432.
   Для тестов отдельная база `safe_city_test`.
4. **Монорепозиторий**: `backend/` и `frontend/` в одном репозитории, в отдельных папках.
5. **Вход: телефон + одноразовый код → JWT** (Bearer). Паролей нет. В dev/test код
   фиксированный (`SMS_MOCK_CODE`, по умолчанию `0000`); реальный SMS-провайдер подключается
   позже без изменения API.
6. **«Панель служб» = панель модератора.** Роль `moderator`; экран тот же, смысл другой
   (никаких реальных служб).
7. **«Помогу» и «Потеряно/найдено» закладываем в модель данных и API сразу**,
   интерфейс во фронте — следующими этапами.
8. **API повторяет контракт `frontend/src/services/api.js`** (те же URL под `/api`, JSON в camelCase).
   Минимальные правки фронта делает бэкенд-разработчик: токен в заголовке, шаг ввода кода,
   `VITE_USE_MOCK=false`, адаптеры в `api.js`.
9. **Бэкенд — чистый REST**: мутации возвращают созданный/изменённый объект. Если компонентам
   фронта нужен весь список (как сейчас в моках), `api.js` сам перезапрашивает список.
   Компоненты страниц при этом не меняются.
10. **Оформление — забота фронта.** Цвета, иконки, «12 мин назад», «650 м» сервер не хранит.
    Сервер отдаёт `level`/`type`/`category`, ISO-время `createdAt`, координаты и расстояние
    в метрах (если передать свои координаты). Исключение — статичные справочники
    (службы, памятки): там иконка/цвет — часть контента.
11. **Справочники (службы, памятки, типы меток, категории карты, города) — статичные данные
    в коде бэкенда** (`app/reference/`), отдаются через `GET /api/reference`.
    Пользовательские данные и справочные точки карты (`places`) — в БД.
12. **Чтение публичное, запись — только с токеном.** Карта, лента и справочники доступны без
    входа; создание меток, SOS, контакты, отклики — после входа; панель — только `moderator`.
13. **Фото** храним на диске в `backend/media/` и раздаём как статику `/media/...`;
    до 4 фото на метку, jpg/png/webp, до 5 МБ.
14. **Push/WebSocket в MVP нет** — фронт перезапрашивает данные. Реалтайм — после MVP.
15. **Стиль кода обязателен**: ruff (бэк), ESLint + Prettier (фронт), pre-commit-хуки,
    сообщения коммитов в формате Conventional Commits. CI на GitHub Actions повторяет проверки.
16. **После каждого этапа — автотесты (pytest) + ручная проверка в браузере**
    (встроенный браузер Claude или Helium MCP): Swagger `/docs`, а после интеграции — сам фронт.

## 2026-11-10 — этап 1, вход и профиль

17. **Телефон нормализуется к `+7XXXXXXXXXX`.** Принимаем `+7 912 ...`, `8 (912) ...`, 10 цифр.
    Только российские номера, остальное — 422.
18. **Код: 4 цифры, живёт 5 минут, 5 попыток**, потом 429. Новый код гасит прежние.
    В базе только HMAC-SHA256 от `телефон:код` с ключом `JWT_SECRET` — смена секрета
    делает неиспользованные коды недействительными (это нормально).
19. **В dev/test код всегда `SMS_MOCK_CODE`** и пишется в лог сервера строкой `[SMS MOCK] +7...: code 0000`
    (латиницей — консоль Windows портит кириллицу). В `prod` код случайный.
20. **Повторная регистрация до подтверждения** обновляет имя/город и шлёт новый код;
    после подтверждения — 409 «войдите». Вход неизвестного номера — 404.
21. **JWT живёт 7 дней**, в токене только `sub` = id. В `prod` сервер не стартует,
    если `JWT_SECRET` дефолтный или короче 32 символов.
22. **Модератор назначается командой** `uv run python -m app.cli set-role <телефон> moderator`
    (пользователь должен сначала зарегистрироваться).
23. **В `PATCH /users/me` null для обязательных полей игнорируется**, а не ломает запрос.

## 2026-11-10 — этап 2, справочники

24. **`GET /reference` отдаёт статичные справочники одним ответом**: `services`, `guides`,
    `incidentTypes`, `mapCategories`, `cities`, `sosWaitingTips`, `reportNextSteps`,
    `maxContacts`. Тексты перенесены из `frontend/src/mock/data.js`.
25. **Строки-подписи собирает фронт.** У памяток вместо `stepsCountLabel`/`metaSubtitle`
    приходят `source` («Памятка МЧС») и `readMinutes`, число шагов — `steps.length`.
    У шагов после отправки метки нет поля `number`, это индекс + 1.
26. **Типов меток 9, у каждого `group`**: `danger` (6 типов формы «Сообщить»), `help`
    (`help_needed`), `lost_found` (`lost`, `found`). Форма в макете показывает только `danger`.
    Поле `defaultService` переименовано в `hint` — служб в системе нет.
27. **Шаги после отправки метки переписаны под идею продукта**: «метка появится на карте» →
    «модератор проверит» → «уведомление о статусе» (в макете был «диспетчер передаст службе»).
28. **Город пользователя — только из справочника** (`register`, `PATCH /users/me`), иначе 422
    «Выберите город из списка». Пробелы по краям обрезаются.
29. **`GET /places`**: фильтр `category` можно повторять; `lat` и `lng` передаются вместе
    (одна координата — 400). С координатами в ответе `distanceMeters` (метры по прямой,
    гаверсинус, `app/core/geo.py`) и сортировка от ближней точки; без них `distanceMeters: null`
    и порядок по `id`.
30. **Сид точек Москвы — CLI-командой** `uv run python -m app.cli seed-places`, а не миграцией:
    повторный запуск добавляет только недостающие точки (ключ — название + адрес, уникальный
    индекс в БД). Набор демонстрационный: координаты приблизительные, «опасные места» выдуманы,
    телефоны — номера служб 101–112.

## 2026-11-10 — этап 3, экстренные контакты

31. **Лимит 5 контактов — 409**, проверка под блокировкой строки пользователя
    (`SELECT ... FOR UPDATE`), чтобы параллельные запросы не обошли лимит.
32. **Номер контакта нормализуется** как номер пользователя. Один номер дважды у одного
    пользователя — 409 (уникальность `user_id, phone`); свой номер — 400.
33. **Чужой контакт — 404, а не 403**: не раскрываем, что такой id существует.
34. **`relation` по умолчанию «Близкий»** (как во фронте), пустая строка тоже даёт «Близкий».
    `notifyMethod` — `sms` или `sms_push` (по умолчанию). Подпись «SMS и push» рисует фронт.
35. **`position`** — порядок в списке, новый контакт встаёт в конец; после удаления номера
    не сдвигаются. Ручной сортировки в MVP нет. `POST /contacts` отвечает 201.
36. **Контакты удаляются вместе с пользователем** (`ON DELETE CASCADE`).

## 2026-11-10 — этап 4, метки

37. **Координаты метки необязательны в запросе**: форма во фронте шлёт только адрес. Нет `lat`/`lng` —
    берём `lastLat`/`lastLng` пользователя, нет и их — 400 «Укажите место на карте или включите
    геолокацию». Одна координата без другой — 422.
38. **Тип метки проверяется по справочнику** (`incidentTypes`), включая `help_needed`, `lost`, `found`.
39. **Автор на карте — «Полина И.»** (фамилия сокращена), телефона нет. Анонимная метка — `author: null`
    для всех, кроме самого автора. Модератор видит полное имя и телефон всегда (этап 7).
40. **Отклики**: всем — `responsesCount` (активные), вошедшему — `myResponse`, автору — список
    `responses` с именами и телефонами откликнувшихся (иначе не связаться). На свою метку — 400,
    повторно — 409, на закрытую — 409. Отмена ставит `cancelled`, повторный отклик оживляет ту же
    запись. При закрытии метки активные отклики становятся `done`.
41. **Скрытая метка (`hidden`)** не попадает в общий список и даёт 404 всем, кроме автора и модератора.
    `?mine=true` (нужен вход) отдаёт свои метки, включая скрытые. Фильтр `status=hidden` — 422.
42. **Автор может** править описание и адрес и закрыть метку (`status: "closed"`); другие статусы
    ставит только модератор. Закрытую или скрытую метку менять нельзя — 409. Чужую — 403.
43. **Радиус**: `radius` (1–50 000 м) только вместе с `lat`/`lng`; в SQL — грубый квадрат, точный круг
    в Python. Порядок — от новых к старым, `limit` по умолчанию 100 (до 500).
44. **Фото**: формат определяем по первым байтам (JPG/PNG/WebP), заголовку клиента не верим. Больше
    5 МБ — 413, не картинка — 400, больше 4 на метку — 409. Если в пачке есть плохой файл, не
    сохраняется ни один. Файлы — `MEDIA_DIR/incidents/<id>/<uuid>.<ext>`, в ответе `url` от корня
    сервера (`/media/...`). В тестах `MEDIA_DIR` — временная папка.
45. **Неверный токен на публичном эндпоинте — 401**, а не гостевой ответ: фронт поймёт, что сессия истекла.
    Без токена — обычный гость (`OptionalUser`).
46. **Все POST, создающие запись, отвечают 201.**

## 2026-11-10 — этап 5, SOS

47. **SOS никогда не блокируется из-за геолокации.** Все поля тела необязательны; нет координат —
    берём последнее место пользователя, нет и его — сигнал уходит с `lat: null`. Переданные координаты
    сохраняются пользователю как `lastLat`/`lastLng`/`lastAddress`.
48. **Один активный SOS на пользователя** — частичный уникальный индекс `WHERE status = 'active'`.
    Повторное нажатие (и параллельные нажатия) не создают второй сигнал: `POST /sos` отвечает 200 тем же
    сигналом с обновлённым местоположением. Новый сигнал — 201.
49. **Доставка имитируется**: на каждый контакт с `receivesSos` создаётся `sos_deliveries`, мок-SMS
    пишет в лог `[SMS MOCK] +7...: SOS from user #1 at lat,lng` и ставит `delivered`. При отмене
    доставленным контактам уходит мок-сообщение об отмене. Реальный провайдер — в `services/sms.py`.
50. **В доставке копируются имя, «кем приходится» и номер контакта**: если контакт удалят, история SOS
    останется (`contactId` станет `null`).
51. **`POST /sos/active/cancel`** отменяет текущий сигнал без id (так вызывает `api.js`). Чужой сигнал — 404,
    уже завершённый — 409. Статус `resolved` ставит модератор (этап 7).
